# PART 0 — Verification

## 0.1 The settled architecture, and what this document has to specify

The decision is made and is not relitigated here:

> **Schema is generated at DEVELOPMENT time from SQL files. The output is COMMITTED.
> A UNIT TEST compares the committed file to the live database. Nothing parses SQL at
> runtime.**

| Concern raised | How it resolves under this architecture |
|---|---|
| "the registry becomes a fifth copy of the schema" | It is not a copy, it is an **artefact**. A copy is trusted and can drift silently; an artefact is regenerated by one command and **its drift is a test failure**. |
| Overlay drift (labels / writable / sensitivity) | The comparison test asserts **every overlay key exists in the derived schema** (`R-POL-4`). |
| A hand-ALTERed column | The same comparison test fails (`column_undeclared`). |
| Runtime cost | **Zero.** Nothing runs at request time. |

Also settled, and carried without change: **labels are PROPOSED from `ProjectDcs`
requirements and human-confirmed.** Proposals are marked `unverified` until confirmed.
The codemeta lesson — *generated metadata must never be authoritative and silently
wrong* — is the reason. §5.

What remains to be specified, and is the body of this document:

1. the generator (§1),
2. the committed file format (§2),
3. the comparison test (§3),
4. the runtime boundary (§4) — **the part most likely to be got wrong**,
5. the label-proposal workflow (§5),
6. the phased plan (§6).

## 0.2 The prototype **[V]**

To avoid writing this document on assumptions, a prototype was built and executed
against the real corpus. It is **not** production code and it lives outside every
repo, at `/tmp/opencode/schemaproto/`:

| File | Lines | What it is |
|---|---|---|
| `lib.php` | ~290 | `frame()` — FA's `db_import()` framing loop transcribed 1:1; `strip_comments()`; `paren_body()` / `split_top()` (quote- and paren-aware); `parse_column()`; `Acc` (the accumulator: `create_table`, `alter_table`, ordinal handling, ownership flag); `canonical()`; `replay()`. |
| `proto.php` | ~120 | Driver for `ksf_FA_Calendar`: A1-only replay, A2 glob replay, union replay, JSON determinism check. |
| `census.php` | ~45 | Driver across **every** module directory. |

**Two things it is deliberately NOT:** it is not the `ManifestReader` (which needs
`token_get_all()` over `hooks.php`, per `R-ORD-2`), and its ordering is a plain
name-sorted sweep of `sql/*.sql` — which is authority **A3**, the one that is
*wrong*. That was on purpose: A3 is the naive baseline every derivation starts from,
so running it first shows what the real algorithm must fix.

### 0.3 What the prototype proved **[V]**

**Corpus totals from the generator itself** (A3 name-ordered sweep of
`sql/*.sql`, module-owned files, `vendor/` excluded):

> **44 module directories · 195 tables · 1,935 columns**

This is an **upper bound**, not the answer — §0.3.1 shows why A3 over-counts.

`ksf_FA_Calendar` under the union replay (`R-ORD-3`) reproduces the prior document's
live-verified finding exactly **[V]**: `fa_cal_entries` resolves to **49 columns**
including `delta` and `closed_at` (A1 upgrade files only, §0.4 of the derivation
design) **and `fork_group_id` (A2 only, the orphaned `upgrade_2.1.0.sql`)**. A1-only
replay omits `fork_group_id`; A2-only replay also omits it *as a table* because
`upgrade_2.1.0.sql` alone never creates `fa_cal_entries`. **Union is required, and
this is now re-proved by execution rather than by argument.**

### 0.3.1 `R-ORD-1` — the decisive new proof: A3 produces an **EMPTY schema** for two modules **[V]**

This is the strongest single result in this document and it was not previously known.

`ksf_FA_ManufacturerConsolidation/sql/` contains exactly two files:
`install.sql` (4 × `CREATE TABLE IF NOT EXISTS`) and `uninstall.sql`
(4 × `DROP TABLE IF EXISTS`). **Alphabetically `install.sql` sorts first**, so under
authority **A3** the sweep creates four tables and then drops all four:

```
A3 (alphabetical: install.sql, uninstall.sql)  ->  0 tables
A1 (manifest:    install.sql only)             ->  4 tables
     ksf_supplier_moq_rules, ksf_consolidation_groups,
     ksf_consolidation_lines,  ksf_consolidation_recommendations
```

Same for **`ksf_FA_StockReservations` (1 table → 0)**.

| Replay | Result |
|---|---|
| `ksf_FA_ManufacturerConsolidation`, alphabetical | **0 tables** |
| `ksf_FA_ManufacturerConsolidation`, manifest order | **4 tables** |

**So the naive assumption "just replay the directory in name order" is not merely
incomplete — for two modules it is catastrophically wrong, in the one direction
(aliasing/uniqueness aside) that a human reviewer cannot notice.** The derivation
design stated `R-ORD-1` as a principle; this is a runnable fixture that proves it,
and it is the acceptance test for the ordering algorithm in §1.3.

### 0.3.2 `INDEX` is a live alias for `KEY` in this corpus — 85 occurrences **[V]**

The prior census (§0.3 of the derivation design) reported `KEY \`…\`` ×291.
Re-counted, module-owned files only, `vendor/` excluded:

| Spelling | Occurrences |
|---|---|
| `KEY \`name\` (…)` | **302** |
| `INDEX \`name\` (…)` | **85** |
| `UNIQUE KEY \`name\` (…)` | **88** |

`INDEX` is MySQL's synonym for `KEY`. **The prototype's first version, written against
the prior census, parsed all 85 as a COLUMN named `INDEX`** — a phantom column with
type `unknown` appeared in `fa_cal_attachments`. Files affected include
`ksf_FA_Calendar/sql/upgrade_1.4.0.sql`, `upgrade_1.5.0.sql`,
`ksf_FA_Notes/sql/install.sql`, `ksf_FA_Attachments/sql/install.sql`,
`ksf_bank_import/sql/update.sql`, `ksf_FA_Woocommerce/sql/schema.sql`,
`ksf_FA_StockTurnover/sql/install.sql`, `ksf_FA_StockReservations/sql/install.sql`,
`ksf_FA_PurchaseOrderTracking/sql/install.sql`, `ksf_FA_Upc2Item`,
`ksf_FA_ManufacturerConsolidation/sql/install.sql`.

**Consequence for the design:** the column/index discriminator must accept
`(UNIQUE )?(KEY|INDEX)`, and the fixture suite (§1.5) must pin the count at 85 so a
future regression is caught. This is exactly the class of defect the golden-file
fixture suite exists to prevent, and it was found by **running** the thing rather
than reasoning about it.

### 0.3.3 FA's framer **keeps** `--` comment lines inside a statement — the generator must strip them **[V]**

`maintenance_db.inc:374` appends the **entire trimmed line**, comment lines included,
into the statement buffer. MySQL strips them at execution; the generator must
therefore remove them **after framing and before any quote-aware splitting**.

The prototype omitted this at first. It produced **11 `UNPARSED COLUMN DEF` findings
across 4 modules**, and the mechanism is worse than "a phantom column":

- A `--` comment **containing a comma** splits a `CREATE TABLE` body item in half,
  because `split_top()` is comma-separated and quote-aware but not comment-aware.
- A `--` comment **containing a single quote** (`ksf_FA_DataIntegrity`: `-- 'full'`)
  desynchronises quote-tracking for everything after it, so the remainder of the
  statement is mis-parsed.

| Module | Findings before stripping |
|---|---|
| `ksf_FA_DataIntegrity` | 4 (incl. `'full'` and `-- 'purchase'`) |
| `ksf_FA_SerialNumber` | 2 |
| `ksf_FA_Warehouse` | 1 |
| `ksf_bank_import` | 3 |

After adding a quote-aware `--` / `/* */` stripper: **all 11 findings gone, and the
corpus column count rose 1,931 → 1,935** — four commented-out column definitions had
been splitting body items and losing the column that followed each one.

**This is not lossy, and that is the point.** Stripping comments reproduces what
MySQL executes. A column that a module author disabled by commenting it out **does
not exist in the database**, so it must not appear in the committed file either.

### 0.3.4 `ALTER` shapes the prior census under-specified **[V]**

The derivation design's ALTER sub-clause census (§0.3) listed `ADD COLUMN` ×32,
`MODIFY` ×15, `ADD INDEX` ×10, `ADD CONSTRAINT … UNIQUE` ×2, `ADD KEY` ×1,
`DROP INDEX` ×1. The prototype found two shapes in the **same** statements that the
census's labels did not isolate, both in `ksf_FA_Calendar`:

- **`ADD INDEX IF NOT EXISTS \`idx_…\` (\`col\`)`** — the `IF NOT EXISTS` variant,
  used for **all 9** of Calendar's `ALTER`-added indexes. A regex modelled on
  `ADD INDEX <name>` does not match it.
- **`ADD CONSTRAINT \`fk_…\` FOREIGN KEY (…) REFERENCES (…) ON DELETE SET NULL`** —
  an FK added by `ALTER`, not by `CREATE TABLE`. 10 of these in Calendar alone
  (`upgrade_1.1.0.sql`, `upgrade_1.2.0.sql`). **Foreign keys are not only a
  `CREATE TABLE` phenomenon in this corpus**, which the prior document's §0.10.2
  table did not say.

Neither is exotic; both are in files the census already counted. They were found by
running the accumulator and reading its `UNCLASSIFIED` findings.

### 0.3.5 Two more `NotReplayable` placeholder files **[V]**

`ksf_FA_Rep_SalesGroups/sql/install.sql` and `ksf_FA_Workflow/sql/install.sql` are
**entirely comment lines — zero framed statements.** Same class as the known
`ksf_FA_Wallet/sql/fa_wallet_transactions.sql` placeholder. The corpus therefore has
**three** zero-statement `.sql` files, and each must be reported as
`NotReplayable` rather than silently skipped (`R-ORD-4`).

### 0.3.6 The file tree has shapes a flat `glob()` misses **[V]**

| Shape | Example | Consequence |
|---|---|---|
| **Subdirectory inside `sql/`** | `ksf_bank_import/sql/migrations/001_create_transactions_table.sql`, `002_backfill_….sql` | `SchemaMigrationRunner`'s `glob("sql/upgrade_*.sql")` **and** a flat `glob("sql/*.sql")` both miss it. 2 files. |
| **`.sql` at module ROOT, not in `sql/`** | `ksf_FA_ManufacturerConsolidation/install.sql`, `ksf_FA_PurchaseOrderTracking/install.sql` | A `sql/`-scoped scan misses them. |
| **A directory literally named `:`** | `ksf_FA_API/:/sql/install.sql` | **A deploy-recipe quoting bug.** It is a stale pre-fix copy: the real `ksf_FA_API/sql/install.sql` uses `` `0_ksf_api_logs` `` while `ksf_FA_API/:/sql/install.sql` still uses `@TB_PREF@ksf_api_logs` — i.e. it is the version that `db_import()` does *not* substitute (§0.1 of the derivation design). A recursive glob would pick up the wrong file. **Do not `rm` it as part of this work** — it is a separate defect in a separate recipe; file it. |
| **Test fixtures under a module** | `ksf_bank_import/tests/helpers/test_seed_data.sql` | A recursive scan picks up test data as schema. |

**Rule `[D]` `R-ENUM-1`: enumeration is `sql/*.sql` (non-recursive) ∪ whatever the
manifest names, plus an explicit, **reported** subdirectory sweep.** Never a bare
recursive glob.

|---|---|---|

The prototype's final finding count is **16**, and they decompose as:

## 0.5 `[D]` — the one real hole in a SQL-only generator

Two modules create tables **in PHP**, with no `.sql` file **[V]**:

| Module | Tables | Source |
|---|---|---|
| `ksf_FA_AsteriskPBX` | 3 (`fa_asterisk_extensions`, `fa_asterisk_calls`, `fa_asterisk_voicemail`) | `hooks.php:63-107`, `ensure_asterisk_schema()` |
| `ksf_bank_import` | 5 (`bi_config`, `bi_config_history`, `bi_uploaded_files`, `bi_file_statements`, `bi_bank_accounts`) | `hooks.php:167-250` |

**Eight tables a SQL-file generator structurally cannot see.** The derivation design
flagged this as "the one genuine hole in A″"; it remains so, and dev-time generation
makes it *no worse but also no better*. Three options, in preference order:

1. **Move the DDL into `sql/*.sql` and wire it.** Correct, cheap, and it removes the
   hole permanently. Out of scope here (it is module work, not generator work).
2. **`->fromDdl(string)` escape hatch**, an overlay-supplied raw DDL block that the
   *same accumulator* applies. Keeps one code path, keeps it checkable.
3. **Do nothing and emit a `TablesNotInSql` finding.** Honest, but leaves 8 tables
   permanently undeclared and — because `R-POL-4` rejects unknown overlay keys —
   permanently unclassifiable.

**Decision `[D]`: option 2 for v1, option 1 as the migration.** A PHP-created table
is not a special case; it is a table, and the accumulator is the only thing in this
design that is allowed to create one.

# PART 1 — The generator

## 1.1 CLI entry point **[D]**

A single CLI, in `ksf-common-db` (it already owns `TableDefinition` and
`QueryBuilder`; `Schema_Registry_Design.md` §D.2 settles that this package, not a
neutral one, is the right home, and nothing in this design changes it):

```
bin/ksf-schema generate  --module=<name> [--module=<name>…] [--root=<fa_modules>]
bin/ksf-schema check     --module=<name> [--root=<fa_modules>]      # regenerates, diffs vs committed
bin/ksf-schema propose   --module=<name>                            # §5, label proposals only
bin/ksf-schema compare   --module=<name> --company=<id>             # §3, needs a DB
```

| Command | Reads DB? | Writes? | Gate |
|---|---|---|---|
| `generate` | no | the committed artefact | none — **is** the artefact-producing step |
| `check` | no | nothing | **CI gate**: regenerate in memory, byte-compare to the committed file |
| `propose` | no | only `overlay.labels[*].unverified` entries | never in CI; human-invoked |
| `compare` | **yes** | nothing | reports (§3.4) |

**`generate` and `check` are the same code path with a different sink.** `check`
must not be a reimplementation, or the two will diverge — which is the entire failure
mode of the five-copies problem this design exists to remove.

## 1.2 Enumeration **[D]** — built on `R-ORD-4`, refined by §0.3.6

```
enumerate(module):
  1. sqlDir = <root>/<module>/sql
  2. A1 = ManifestReader(hooks.php).orderedFiles()      # R-ORD-2: all shapes S1–S4
  3. A2 = version_sorted(glob(sqlDir/upgrade_*.sql))     # R-ORD-5: version_compare
  4. A3 = sort(names(sqlDir/*.sql), SORT_STRING)         # non-recursive (R-ENUM-1)
  5. REPLAY = [A1 in literal order] then [A2 in version order]   # R-ORD-3 union
  6. REPORT  = every A3 name not reached by A1 ∪ A2, classified:
         OrphanNeverApplied  (schema-bearing DDL FA will never run)
         NotReplayable       (uninstall.sql, seed.sql, zero-statement file — §0.3.5)
         Unreachable         (manifest names a file that does not exist)
  7. REPORT  = subdirectories of sqlDir (e.g. sql/migrations/) as SubdirNotScanned
```

Step 6's classes are `R-ORD-4` unchanged. Step 7 is new, from §0.3.6.

**Non-recursive by rule.** `R-ENUM-1` exists because a recursive glob finds
`kss_FA_API/:/sql/install.sql` (a stale pre-fix copy) and
`ksf_bank_import/tests/helpers/test_seed_data.sql` (test fixtures). Both would be
worse than invisible.

## 1.3 Ordering **[D]** — `R-ORD-1/3/5`, now with a runnable acceptance test

The algorithm is inherited unchanged from the derivation design's `R-ORD-1/3/5`:
**A1's literal order first, then A2's `version_compare` order, unioned.** Every
mutation in the corpus is idempotent (215/215 `CREATE TABLE`s are `IF NOT EXISTS`;
`ADD COLUMN`/`ADD INDEX` without it fail with suppressed `1060`/`1061`), so union is
safe — and mandatory, or `fork_group_id` reads as undeclared forever.

**`ManifestReader` must be PHP-syntax-aware** (`token_get_all()` over `hooks.php`, not
a regex — `R-ORD-2`). A regex `$updates = array(` read finds 19 of 28 modules and
silently misses: the inline-array shape (S2, `ksf_FA_Notes`), the loop-built shape
(S3, `FA_ProductAttributes`), and the three no-manifest modules that call `db_import()`
directly (S4).

**Acceptance test, executable `[V]` — derived from §0.3.1:**

```php
// The ordering algorithm is correct iff replaying the directory in NAME ORDER
// is NOT what it produces. This is the fixture that proves the point.
$manifest = $replayer->filesFor('ksf_FA_ManufacturerConsolidation');
$this->assertCount(1, $manifest);                    // install.sql only
$this->assertSame([], array_values(array_diff(
    $manifest, ['uninstall.sql'])));                 // uninstall.sql NOT in the manifest
$this->assertSame([], $replayer->replay($manifest)->tables());  // via A2 it is empty
$this->assertCount(4, $replayer->replayA1('ksf_FA_ManufacturerConsolidation')->tables());
```

A build that passes this cannot be deriving its order from the filename.

## 1.4 Statement framing — **reuse FA's splitter. Do not write one.** **[V]**

The derivation design settled this decisively (§0.11, §2.6) and the prototype
re-confirmed it by construction. `FaSqlFramer::frame()` is
`maintenance_db.inc:328-374` extracted verbatim: ~40 lines, dependencies only on
`file()` and `str_replace()`, all state in four locals. **Keep the `DELIMITER` branch**
(zero corpus uses today **[V]**; add a fixture pinning that zero) **and keep
`$line_no + 1`** — `db_import`'s error contract is *"SQL script execution failed in
line %d"* (`:484`), and the prototype shows provenance is what makes a finding
actionable:

```
"AFTER target 'date_format' not found in table"   ← useless
"upgrade_1.5.0.sql:12 — AFTER target 'date_format' not found"  ← actionable
```

**Benchmark carried forward, not re-run:** on all 148 real files, FA's framing yields
**333 statements**; `explode(';')` yields 499 non-empty fragments; they agree on
**139/148** files and **FA wins all 9 disagreements**.

**Three additions the prototype forces, all post-framing:**

| # | Addition | Why — evidence |
|---|---|---|
| 1 | **`strip_comments()` after framing, before any splitting.** Quote-aware `--` and `/* */`. | §0.3.3 **[V]**: without it, 11 findings across 4 modules and 4 lost columns. |
| 2 | Accept **`(UNIQUE )?(KEY|INDEX)`** as the index-key discriminator, and `ADD INDEX **IF NOT EXISTS**`. | §0.3.2 **[V]** (85 `INDEX` occurrences); §0.3.4 **[V]**. |
| 3 | Handle **`ALTER … ADD CONSTRAINT … FOREIGN KEY`**. | §0.3.4 **[V]**: 10 in Calendar alone. |

**One addition to `FaSqlFramer` itself that is NOT in the extraction:** the framer
must also return the **`skip`/protect** decision as data even though `$protect` is
always `false` on this path (derivation design §A.2 item 11 **[V]**), so that a future
caller passing `protect = true` cannot silently change the derived schema. **Assert
the argument values rather than assume them.**

**Residual risk, unchanged [UNVERIFIED]:** FA's framing is line-based, so a `COMMENT`
string that itself ends a line with `;` would still be mis-framed. No such file
exists in the corpus **[V]**; what MySQL would do with the result was not tested.
**Matching FA exactly remains correct regardless: where the generator and FA disagree
about where a statement ends, FA wins, because FA is what built the database.**

## 1.6 Prefix resolution — how the generator must **not** disagree with `db_import` **[D]**

`db_import` does, at `maintenance_db.inc:337`:

```php
if ($init) $line = str_replace("0_", $connection["tbpref"], $line);
```

**unconditional, whole-line, textual, and not lexical** — it rewrites `0_` inside
string literals and inside comments too. `ksf_FA_RBAC/sql/install.sql:114` seeds a
description containing the literal text ``'…linked via 0_crm_contacts.entity_id = 0_users.id'``,
which reaches the database as `…1_crm_contacts…1_users.id` for company 1 **[V]**.

**The generator's answer: never perform the substitution at all.**

| Step | Generator | Why it cannot disagree |
|---|---|---|
| 1 | Run `FaSqlFramer::frame()` with `$tbpref = '0_'` — **identity**. | `str_replace("0_", "0_", …)` is a no-op, so the generator's framing is bit-identical to a company-0 replay and the substitution is *deferred*, not reimplemented. |
| 2 | When recording an identifier, strip a leading `0_` and store the **logical** name (`fa_pm_tasks`). | `FaDbAdapter` re-adds the prefix at runtime and *skips* a table already beginning with it (`FaDbAdapter.php:70`), which is why a hardcoded `0_` in runtime SQL becomes `1_0_rbac_…` **[V — `FR-ACL-010-01.md` §2]`. Storing logical names is therefore not a style choice; it is correctness. |
| 3 | Apply the same strip to **FK `REFERENCES` targets**, index names and constraint names. | The prior document flags this explicitly: a `REFERENCES 0_fa_cal_entries` is rewritten textually, so an implementation that un-prefixes the table but not the reference points every FK at a non-existent company-0 table. |
| 4 | Record a `LiteralUnsubstituted` finding for any identifier containing `@TB_PREF@`, `{TB_PREF}`, or `{{MDB}}`. | `db_import` substitutes **only** `0_` **[V]**. `ksf_FA_Logging/sql/install.sql:11` creates `` `@TB_PREF@ksf_log_levels` `` — legal as a backticked identifier, so the statement **succeeds and creates a wrongly-named unprefixed table.** The generator must record that name verbatim and flag it. 33 files still contain the text `TB_PREF` **[V]**. |

**The rule, in one line: the generator stores prefix-free logical names and lets
`FaDbAdapter` do the one substitution, exactly as it already does at runtime — so
there is one prefix-substitution implementation in the system, not two.**

# PART 2 — The committed schema file

## 2.1 Location and granularity **[D]**

**One file per module**, inside the module's own repo, beside the code that depends
on it:

```
<module>/schema/ksf_FA_Calendar.schema.json
```

Chosen over a central store because (a) a module's schema is reviewed in the same PR
as its `sql/` change, (b) the ownership question is then unambiguous — the repo that
owns the `.sql` owns the artefact — and (c) no cross-repo file moves are needed to
adopt it for one module.

## 2.2 The two halves in one file, separated by construction **[D]**

`Schema_Derivation_Design.md` §3.4 `R-POL-4` requires the overlay to be validated
against the derived schema. Dev-time generation makes that validation *free and
unavoidable*: **the generator owns the `derived` block entirely and may only touch
the `overlay` block where a key is absent.**

| | `derived` | `overlay` |
|---|---|---|
| Written by | the generator, **always** | a human, or `propose` (which only ever adds `unverified` labels) |
| If a human edits it | **the next `generate` overwrites it and `check` fails** — which is correct | preserved |
| Content | only what SQL can state | only what SQL cannot |
| Cross-checkable against | `information_schema`, per company | **nothing — by design** |

**This is the structural answer to "the registry becomes a fifth copy."** A copy is
*editable* and *trusted*. This block is neither: it is regenerated by one command and
its divergence from the database is a test failure (§3). A reviewer who edits
`derived` gets a red CI, not a silent divergence.

## 2.3 The format **[D]** — JSON, and why

| Candidate | Verdict |
|---|---|
| **JSON** | **Chosen.** `json_encode` is in the core since PHP 5.2 — **zero dependency**, which matters because `ksf-common-db` must not acquire a dependency (§D.2) and the PHP floor is 7.3. Deterministic ordering is achieved with `ksort` before encoding. |
| YAML | Rejected on the decisive practical fact: **`ext-yaml` is not loaded** (verified: `php -m` shows no `yaml`) **[V]**, so YAML means adding and shipping a parser into a package whose whole justification is having no dependencies. It also buys ambiguous typing (`'no'` vs `false`, `1_` vs int) in a file where a misread key is a silent failure. |
| PHP array | Rejected: it cannot be diffed by anything except `git diff` on executable source, and `return [...]` is not reviewable by a non-programmer — the exact property §2.4 needs. |
| CSV / TSV | Rejected: nested (columns → indexes → columns-with-direction) does not flatten without loss. |

**Diff-friendliness is achieved by four rules, not by the format:**

1. `JSON_PRETTY_PRINT`, one key per line, 4-space indent.
2. `ksort` every map by key; columns carry an explicit `ordinal` so the *ordinal* is
   data, not array order.
3. No timestamps, no hostnames, no generator version inside the compared region —
   they belong in a sibling `_meta` block that `check` excludes from the byte-compare.
4. One table per top-level key, so a diff's hunk boundaries are tables.

Measured: `ksf_FA_Calendar` = **56,293 bytes** of pretty JSON for 12 tables /
49 columns in the worst table **[V]**. That is large but every hunk is human-sized.
**Not yet measured: the diff size produced by a realistic single-column addition
across that file [UNVERIFIED].**

# PART 3 — The comparison test

## 3.1 Name and location **[D]**

> **`CommittedSchemaMatchesDatabaseTest`** — in `ksf-common-db`'s own
> `tests/Integration/`. One test method per `(module, company)` pair; the module list
> and company list come from configuration, not from a hardcoded array.

`check` (§1.1) is a **separate, DB-free** test — `GeneratedArtefactIsUpToDate` —
which regenerates and byte-compares. Two tests, two failures, two different meanings:
one says *"the committed file is stale"*, the other says *"the database is stale"*.

## 3.2 What it asserts

| # | Assertion | Severity | Why |
|---|---|---|---|
| **A1** | every **overlay** key resolves to an entry in the derived schema (table, column, index, FK name) | **error** | `R-POL-4`. *This is the assertion the brief names, and under dev-time generation it is a test rather than a runtime merge-time throw.* |
| **A2** | every column named in a `ProjectDcs` requirement that carries a `@BABOK Related:` reference **exists** in the derived schema | **error** | Requirements are hand-written and rot; `FR-ACL-001-01` names `0_rbac_record_owner`, `.record_group`, `.group_policy`, `.record_exception`, `0_rbac_audit_log` **[V]**. A renamed column must fail the build, not a picker. |
| **A3** | derived column exists in `information_schema` | **error** — `column_missing` | PM's ten CPM columns + `task_dependencies` **[V, live-confirmed]** |
| **A4** | `information_schema` column absent from derived | **warning** — `column_undeclared` | a hand-ALTER. **Never auto-adopted** — that would make `information_schema` the source (§4.3) |
| **A5** | type / length / scale / unsigned equal | **error** — `type_changed` | includes a `MODIFY` that was never applied |
| **A6** | nullability, default, `auto_increment`, `ordinal` equal | error / warning | `ordinal` mismatch means an unapplied `ADD COLUMN … AFTER` |
| **A7** | primary key, unique keys, indexes, FKs equal | **warning** | index drift is a performance defect, not a correctness one |
| **A8** | `engine`, `charset` equal | warning | |
| **A9** | every `findings[]` entry of severity `error` has been **acknowledged** in the file (`acknowledged_findings`) | **error** | so the 16 live findings become a tracked, reviewed list rather than permanent noise |
| **A10** | the count of `UnparsedColumnDef` / `UnclassifiedStatement` is **0** | **error** | §2.5 last row |

**A1 is the overlay-drift assertion and A2 is the requirement-drift assertion.** They
are the two the brief asks for by name, and together they cover both directions:
the overlay cannot reference a column that does not exist, and a requirement cannot
reference a column that does not exist.

### 3.2.1 `R-POL-1` is asserted too **[D]**

| # | Assertion | Severity |
|---|---|---|
| **A11** | the overlay restates no derived fact (type, length, scale, nullable, default, pk, unique, index membership, FK) | **error** |

One line of code, and it is the mechanical guarantee that the overlay cannot grow
into the fifth copy. It replaces `Schema_Derivation_Design.md` §3.4's "the derivation
layer rejects it".

## 3.3 How it connects **[D]**

**The FA-adapter rule applies here unchanged, and this is the one place it is easy to
get wrong:** `AGENTS.md`'s hard rule is that *FA modules use native `db_*` calls at
runtime*. This test is a **CLI/dev-time tool, not a runtime component**, so:

| Context | Transport | Why |
|---|---|---|
| Running **inside** an FA container / on a pod | **`FaDbAdapter`**, calling `db_query`/`db_fetch_assoc` | the same rule, and the same connection FA itself uses, so the comparison is against the same server FA wrote to |
| Running from a dev workstation against a pod | the **PDO** adapter | outside FA; this is exactly what `PdoDbAdapter` exists for, and it is the `DbConnectionInterface`'s second implementation |

Both implement `DbConnectionInterface`. **The test picks by context, not by config
flag** — a flag is a flag somebody points at the wrong thing, and the failure is a
comparison against the wrong server, which is indistinguishable from drift.

Credentials come from the FA `config_db.php` already on the pod, or from an explicit
`--dsn`. **Never** hardcoded; the two pods already carry different credentials with
different passwords (`ksfii_app-mariadb` vs `ksf-mariadb`), and a mismatch reads as
"every column is missing" **[V — `AGENTS.md`]**.

**Cheaper than a column-by-column diff:** one query per table against
`information_schema.COLUMNS` / `.STATISTICS` / `.REFERENTIAL_CONSTRAINTS`, restricted
by `TABLE_SCHEMA = ?` and a prefix `LIKE`. For 195 tables that is 195 indexed lookups
once — negligible. Reuse FA's own comparison primitive shape: `FA_ProductAttributes`
and `ksf_bank_import` already gate with `check_table()`'s `$properties` triple, and
`SHOW COLUMNS` is FA's own comparison **[V]**.

## 3.4 When it runs, and what it does on failure **[D]**

| # | When | Blocking? | Rationale |
|---|---|---|---|
| 1 | **CI, on the schema artefact** — `ksf-common-db` integration job | **no** | **no database in CI.** The DB-free half (`check`) runs here and *is* blocking; the DB half cannot. |
| 2 | **CI, in the module's own repo** — `ksf-common-db` as a dev dependency, against a throwaway DB built by replaying the module's own `sql/` | **yes** | This is the form that *can* gate: build the database **from the manifest replay** and compare. It is the §0.3.1 fixture generalised — declared vs declared-and-instantiated. **The correct CI gate.** |
| 3 | **Nightly**, every pod, every company | **no** | catches hand-ALTERs and deploys that skipped activation |
| 4 | **On activation**, per company, per module | **no** | §3.4.1 |
| 5 | **On demand**, admin health screen | **no** | the visible surface `Schema_Registry_Design.md` §F.3 deferred; drift you cannot see is not managed |

### 3.4.1 It REPORTS; it never blocks activation **[D]**

Carried forward as `R-REC-4`, and it is a hard rule:

> **A schema-comparison finding MUST NOT block FA's extension activation.** The schema
> is a *consumer* input; a failing comparison must not be able to break FA's extension
> activation, which is a documented FA failure mode (`AGENTS.md`: *"the fatal that kills
> the extension page mid-render"*).

Consequences, all specified:

- Every failure is **recorded and surfaced**, never thrown into the activation path.
- The **only** permitted degradation: an `error`-severity finding on a table or column
  the module is *currently writing to* degrades that module's schema resolution to
  `unresolved()` — which is `Schema_Registry_Design.md` §A.6's **permissive-miss**
  rule, not a hard failure.
- Exit code `0` on findings, `1` only on a **test-harness** failure (cannot connect,
  cannot read the artefact). This is what lets forms 3–5 be non-blocking while form 2
  gates.
- `R-REC-2` carries forward: **per `(company, module)`, never global.** Two pods share
  one module tree and not one database **[V]**, and the UAT box and the rootless pod
  were never queried **[UNVERIFIED]**.

# PART 4 — What still needs runtime, and why that is not a fifth copy

This is the section most likely to be misread as a contradiction of the settled
architecture, so it is stated precisely.

## 4.1 The split

| | Generated + COMMITTED | Loaded at RUNTIME |
|---|---|---|
| **What** | the derived schema (structure), the overlay (policy), the findings list | a **compiled in-memory index** of that same file |
| **When** | dev time, by a developer, before review | once per request (or once per request **per pod**, cached) |
| **Where** | `<module>/schema/*.schema.json`, in git | `json_decode()` of the same bytes |
| **Cost** | one command, offline, seconds | one `file_get_contents` + `json_decode` per pod per request |
| **Drift** | detected by `CommittedSchemaMatchesDatabaseTest` | **cannot drift** — it is the committed bytes |

## 4.2 What genuinely still needs runtime, and why **[D]**

**Three things, and only three:**

### 4.2.1 The query builder must know the declared table — and it cannot be precomputed **[D]**

`QueryBuilder::$select` defaults to `['*']` (`QueryBuilder.php:26`) and `from(string)`
stores an **opaque string** with no getter (`:83-88`) **[V]**. So:

- A row-ACL predicate cannot be keyed on the table, because the builder cannot report
  what it is selecting from. `FR-ACL-010-01.md` §5 states this verbatim.
- `SELECT *` cannot be **expanded**, because expansion requires a column list.

Both require a schema **at the moment the SQL is built**, chosen by the value of
`$qb->from(…)` — which is data known only at runtime. Precomputing it would require
predicting every query. **This is not the fifth copy; this is the copy actually being
used, read rather than written.**

### 4.2.2 A declared table must be *carried*, not looked up, for ACL **[D]**

`FR-ACL-010-02` §2.1 is explicit that the column mask must be
`CASE WHEN :canReadX = 1 THEN col ELSE NULL END` **per column** — a wildcard cannot be
masked, because the mask must *name* each column it touches. That means the runtime
holder must be the **compiled form of the committed overlay**, looked up by the
logical table name, keyed to the *declared* table rather than a string the caller
typed. `QueryBuilder::fromDefinition(TableSchema $s)` is the change
(`Schema_Registry_Design.md` §E.1 item 1); it is a **v1.1.0 additive release** and
changes no existing signature.

### 4.2.3 `information_schema` cannot be the runtime source **[D]**

`Schema_Registry_Design.md` §0.7: the engine only reads `information_schema`, and it
does not give a display label, a description, an enum member list, writable-vs-derived,
a sensitivity class, or a relationship edge. It **also** cannot be a *dependency*:
`FR-CLAC-103`'s `NullColumnPolicy` guarantee requires a registry miss to be
**permissive**, so a database round-trip per request would make the ACL path depend on
DB latency and on the DB being up. **A query builder that cannot build SQL when the
DB is down is not a builder.**

## 4.3 Why this is not the "fifth copy" problem **[D]**

The prior documents' five sources (`Schema_Derivation_Design.md` §5.1) are five places
a human *writes* schema and each can be wrong in a different direction, with nothing
to compare them. The count was never the problem; **the number of independent,
mutually-unchecked *writings* was.**

| | Five copies | This design |
|---|---|---|
| Who writes it | five different authors | **one generator** (derived) + one human (overlay, 5 keys) |
| Can it drift silently | **yes** — every one of the five | **no** — `derived` is regenerated; drift is a red test |
| Checked against the DB | no | **yes**, per `(company, module)`, on a schedule and at activation |
| Checked against requirements | no | **yes** — assertion A2 |
| Runtime cost of the registry | parse + build, per request | `json_decode` of committed bytes, per request |

**The runtime copy is not a fifth copy because it is not a *declaration*.** It is a
parsed, cached **read** of the single committed declaration. Delete it and it is
regenerated byte-for-byte; there is nothing to reconcile because nothing was written.

**The residual risk, stated honestly:** a committed file *can* still be stale relative
to the database, because the database can drift after the file was written — the
hand-ALTER case. That is why §3's test exists and why form 3 is nightly. **The
artefact removes the class of error where schema was restated by hand; it cannot
remove the class where the database was altered by hand.** Those are different
problems and only one of them is solved by committing a file.

# PART 5 — Label proposals from `ProjectDcs`

## 5.1 The rule **[D]**

> **A generated label is never authoritative. Every proposal ships `state:
> "unverified"` and must be confirmed by a human before it is used for anything
> consequential.**

This is the codemeta lesson, and it is the reason the whole mechanism is two-staged:
*generated metadata that is authoritative and silently wrong is worse than no
metadata*, because it is trusted and cannot be questioned.

## 5.2 The proposal algorithm **[D]** — **RECOMMENDED, quality UNPROVEN**

```
propose(module):
  for each derived column C:
     1. if C.comment is a well-formed enum list ("a, b | c")  -> SKIP (that is data, not a label)
     2. evidence = collect():
          a. every ProjectDcs/*.md (BR-*, FR-*, UC-*, UAT-*) under the module's repo
             AND under ksf_Architecture_Docs/Requirements/ whose text names C
          b. the column's own SQL COMMENT, if it is not an FK hint
             ("FK to 0_x.y" is a relationship, not a label — §2.4.2 never auto-promotes)
          c. a camelCase->snake_case humanisation of C.name
             (project_manager -> "Project manager")   [Schema_Registry_Design.md §E.3]
     3. if (a) names C inside a document with a @BABOK Related: header:
             label   = the nearest heading/table-cell phrase describing C
             source  = "<FR-ID> §n"
             state   = "unverified"          -- ALWAYS, even at the best confidence
        elif (b):
             label   = humanise(comment)
             source  = "COMMENT: sql/<file>:<line>"
             state   = "unverified"
        else:
             label   = humanise(C.name)
             source  = "derived"
             state   = "unverified"
     4. never overwrite an existing label; never clear a `confirmed` one
```

**Rule 3a is the highest-value path and the only one worth piloting first:** the
`Requirements/` corpus is not aspirational prose. `FR-ACL-001-01-ownership-schema.md`
names specific tables and specific columns with `@BABOK Related:` headers, and
`FR-CAL-010-001` enumerates the Calendar entry fields with their real requirements
**[V]**. **A document that names a column is the closest thing to a label that exists
in this codebase, and it is machine-findable.**

## 5.3 The human-confirmation workflow **[D]**

```
developer:  ksf-schema propose --module=ksf_FA_Calendar
           → rewrites ONLY overlay.*.label where absent, all state:"unverified"
reviewer:   reads the diff. For each proposal, one of:
              keep    → change "state": "unverified"  →  "confirmed"
              edit    → change "value", and "state" → "confirmed"
              reject  → delete the whole label object
           commit with the PR that needed it
CI:         assertion A1 still applies — a label naming a dropped column is an error
```

| Decision | Rationale |
|---|---|
| **`unverified` is the default and proposals never auto-confirm** | codemeta lesson; §5.1 |
| **A proposal only ever *adds* to the overlay, never edits `derived`** | the two halves keep separate custodians (§2.2) |
| **Confirmation is a one-word diff** (`unverified` → `confirmed`) | so confirming is cheap enough that people do it; if it were a separate registry it would not be |
| **`propose` is never run in CI** | a CI that rewrites files is a CI that fights the developer |
| **A rejected label may be re-proposed later** | but only if the evidence improved; otherwise it stays gone |

## 5.4 Honesty about proposal quality **[UNVERIFIED]**

**Proposal quality is unproven and I did not measure it.** Specifically:

- I did **not** run step 2 against the real corpus, so I do **not** know the hit rate
  of path 3a (requirement names the column). It is the *intended* best path and it is
  plausible from reading four requirement files — that is not evidence.
- The `humanise()` fallback is the same fallback `Schema_Registry_Design.md` §E.3
  already requires for a **missing** label, so on its own it adds nothing; it is a
  floor, not a feature.
- **The corpus has a documented reason to be suspicious of prose.** §0.3 in the
  derivation design records that three claims came from words **inside `COMMENT`
  strings** (false positives), and §2.1 notes `0_rbac_team_members`' FK comment is
  *already known to be wrong*. **`COMMENT` is developer prose, not data, and this
  design never treats it as data.**
- The requirement corpus itself is uneven: `CampaignBuilder_Analysis.md` §6.3 and
  `EmailManager_Analysis.md` record `ProjectDcs` documents that are bundled stubs,
  1-line files, or that **describe the opposite module** **[V]**. A label proposed
  from a stub requirement is worse than no label.

**Therefore: pilot, do not generalise.**

| Pilot | Scope | Success criterion |
|---|---|---|
| **P1** | `ksf_FA_Calendar` — 12 tables, 49+ columns, and its `ProjectDcs/` is real | ≥60% of proposals accepted as-is by the reviewer; every rejection is recorded with a reason |
| **P2** | `ksf_FA_RBAC` — small (4 tables) and requirement-rich (`FR-ACL-001-01` names specific columns) | tests path 3a in isolation |
| **Gate** | if P1 acceptance <30%, **stop** and fall back to `humanise()` + a hand-written label block | the cost of a wrong label is a wrong picker entry; it must be cheap to abandon |
